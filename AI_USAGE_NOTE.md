## 2. What Was Generated by Antigravity
The Antigravity assistant generated the end-to-end architecture and implementation of the SALESTORM prototype across Phases 1 through 7:

1. **Database & Storage Layer (`app/db.py`)**:
   - SQLite schema initialization with `CHECK` constraints (`available_quantity >= 0`, `reserved_quantity >= 0`, `sold_quantity >= 0`, and `available + reserved + sold = total_stock`).
   - Concurrency tuning pragmas: `journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 30000` ms, and `foreign_keys = ON`.
   - Context manager connection factory with automatic transaction commit/rollback and retry logic on database lock contention.

2. **Domain Models (`app/models/`)**:
   - Data structures for `Inventory`, `InventoryReservation`, `Payment`, `Order`, `OutboxEvent`, and `OrderState`.
   - State Machine enforcing valid state transitions (`CREATED` -> `PAYMENT_PENDING` -> `CONFIRMED` -> `PROCESSING` -> `SHIPPED` -> `OUT_FOR_DELIVERY` -> `DELIVERED`).

3. **Repository Abstractions (`app/repositories/`)**:
   - Abstract `InventoryRepository` interface.
   - `SqliteInventoryRepository`: High-performance single atomic conditional UPDATE (`WHERE product_id = ? AND available_quantity > 0`).
   - `PessimisticInventoryRepository`: Mutex-guarded read-then-write simulation (`SELECT ... FOR UPDATE` semantics).
   - `ReservationRepository`, `PaymentRepository`, `OrderRepository`, and `OutboxRepository`.

4. **Service & Gateway Architecture (`app/services/`)**:
   - `ReservationService`: Mandatory `Idempotency-Key` validation, fast-path lookup, and atomic stock reservation.
   - `MockPaymentGateway`: Idempotent ledger, 95% success, 5% failure, and network timeout simulation.
   - `PaymentService`: All-or-nothing transactional payment settlement, inventory transition, and outbox event recording.
   - `PaymentReconciliationService`: Background resolution of `UNKNOWN` timeout payments.
   - `MockOrderService`: Simulated downstream order processing with 30-second outage injection toggle.

5. **Asynchronous Background Workers (`app/workers/`)**:
   - `OutboxWorker`: Transactional Outbox processor protected by a 3-state Circuit Breaker (`CLOSED`, `OPEN`, `HALF_OPEN`), exponential retry backoff, and dead-letter queue.
   - `ExpiryWorker`: High-concurrency reservation TTL reaper using conditional multi-worker safe updates.

6. **Automated Testing & Simulation (`tests/`, `simulation/`)**:
   - Pytest scenario test suite (`tests/test_hackathon_scenarios.py`) validating the 6 core distributed design assumptions.
   - 10,000-customer simulation harness (`simulation/load_test.py`) with duplicate requests, simulated outage, and comparative benchmark runner (`--compare`).

## 3. What Was Reviewed and Corrected by the Engineer
During iterative development and testing, several critical system-level adjustments, bug fixes, and architectural corrections were made:

### A. Environment Isolation & Package Management
- **Correction**: Enforced using a dedicated virtual environment (`.venv`) for all Python packages and test execution rather than global system Python.
- **Impact**: Clean isolation of dependencies, predictable versions, and reproducible test results across developer environments.

### B. Windows PowerShell Compatibility
- **Issue**: Standard bash curl commands failed in Windows PowerShell because `curl` is aliased to `Invoke-WebRequest`, throwing parameter binding errors on `-H "Content-Type: application/json"`.
- **Correction**: Rewrote all execution scripts and documentation to use PowerShell-native `Invoke-RestMethod` with hashtable headers (`-Headers @{ "Idempotency-Key" = ... }`) and `curl.exe` with properly escaped quotes.

### C. Windows Console Unicode Encoding
- **Issue**: Console logs containing emojis (e.g., `🚀`, `⚠️`, `✅`) raised `UnicodeEncodeError: 'charmap' codec can't encode character` on standard Windows PowerShell `cp1252` encoding.
- **Correction**: Replaced all console status output with clean, portable ASCII strings (e.g., `[OK]`, `[RETRY]`, `[CIRCUIT OPEN]`).

### D. SQLite Concurrency & Lock Starvation
- **Issue**: Firing 10,000 unthrottled concurrent asyncio tasks against SQLite resulted in `database is locked` errors due to single-writer serialization.
- **Correction**: 
  - Raised SQLite `busy_timeout` to `30000` ms.
  - Implemented an `asyncio.Semaphore` / worker pool (`concurrency = 50`) in the load testing engine. This eliminated database contention while preserving a high throughput of ~210 req/s.

### E. Circuit Breaker Behavior During Downstream Outage
- **Issue**: During the simulated 30-second `OrderService` outage, the outbox worker continued cycling and rapidly incremented retry counts, prematurely pushing valid orders into `DEAD_LETTER` status before the service recovered.
- **Correction**: 
  - Adjusted `OutboxWorker` to check circuit breaker state before incrementing event retry counts. When the circuit is `OPEN`, processing halts early without penalizing the event.
  - Added an automated `retry_dead_letter()` step after outage restoration to ensure zero dropped orders and 100% reconciliation.

### F. Foreign Key Integrity in Unit Tests
- **Issue**: Direct insertion of `Order` or `OutboxEvent` records in isolation tests failed with `sqlite3.IntegrityError: FOREIGN KEY constraint failed` because SQLite foreign keys (`PRAGMA foreign_keys = ON`) require a valid `reservation_id`.
- **Correction**: Updated test fixtures to create parent `InventoryReservation` records before triggering downstream order and outbox flows.

### G. SQLite Transaction Upgrades & Context Manager Generators
- **Issue**: Under heavy multi-threaded test execution, Python's default `BEGIN DEFERRED` transactions caused simultaneous connections to acquire `SHARED` read locks and subsequently deadlock when upgrading to `RESERVED` write locks (`sqlite3.OperationalError: database is locked`). An initial attempt to loop inside `@contextmanager` caused `RuntimeError: generator didn't stop after throw()`.
- **Correction**: Configured `isolation_level = "IMMEDIATE"` on SQLite connections and ensured transactions initiate with `BEGIN IMMEDIATE;`. This enforces write ordering upfront without upgrade deadlocks, allowing threads to wait cleanly on `busy_timeout = 30000` ms.

### H. Concurrent Idempotency Under Maximum Contention
- **Issue**: When 50+ concurrent requests hit `/pay` with the exact same `Idempotency-Key`, earlier implementations checked `reservation.status` outside the database transaction. A racing thread would observe `CONFIRMED` from a concurrent winner before that winner's payment record was committed, prematurely rejecting with `400 Bad Request`.
- **Correction**: Serialized reservation validation and gateway charge inside the transaction with double-checked idempotency lookups. Concurrent duplicate requests now wait for the write lock, observe the winner's committed payment, and return `200 OK` with the matching payment record.

### I. Honest Empirical Analysis on SQLite vs Distributed Production
- **Review & Correction**: Audited the comparative benchmark numbers and rejected misleading marketing assertions. On SQLite, both atomic updates and pessimistic locks serialize through the single-writer database lock (`PAGER_LOCK`), yielding identical throughput within run-to-run noise (~190 req/s). Re-anchored the architectural justification for atomic updates on distributed design principles: absence of process-bound memory state (`threading.Lock` cannot protect across multiple pods/containers) and direct alignment with row-level locking on Postgres/MySQL.
